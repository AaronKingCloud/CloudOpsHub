1. What CloudOps Hub is

A website that shows the health of your infrastructure (servers, VMs, cloud accounts) in one place, and tells you what needs attention right now.

Think of it as a control room screen. Instead of logging in to every server, NAS and cloud console separately, you open one dashboard and see:

  • Summary numbers: how many devices are online, offline, and how many alerts are active
  • Charts: CPU over time, memory and storage per device
  • Alerts: "nas-01 storage exceeds 90%", "backup-vm is offline"
  • Devices and cloud accounts: tables with status and usage
  • Live AWS data: your EC2 instances and their CPU from CloudWatch

Who it's for

TierAudienceIdea
HomelabSelf-hosters, enthusiastsMonitor home servers, NAS, Pi-hole, Plex
ProPower usersHistory, backups, security insights
BusinessSmall teamsRoles (RBAC), cloud integrations, governance

The three building blocks

Almost every web app has the same three parts, and so does this one:

FrontendThe website you see in the browser. Built with React. Lives in frontend/.
BackendA program on a server that answers questions like "list my devices". Built with Python + FastAPI. Lives in backend/.
Data sourcesWhere the answers come from: a small user database (SQLite), sample "mock" data, and AWS for real cloud data.
Restaurant analogy The frontend is the dining room and menu. The backend is the kitchen. The API is the waiter carrying orders (requests) and plates (JSON data) between them. The data sources are the fridge and suppliers.

2. The big picture

This one diagram is the whole system. Everything else in this guide zooms into one of these boxes.

FrontendBackendDataCloud (AWS)

In words

  1. You open the website. Your browser downloads the frontend (HTML, CSS and JavaScript built from React code).
  2. The frontend needs data, so it sends a request to the backend, for example GET /api/devices.
  3. The backend checks who you are (if the page needs login), gets the data from the right place, and sends it back as JSON (plain text data).
  4. The frontend turns that JSON into tables, badges and charts on your screen.
Two ways to run it Mock mode: the frontend uses its own sample data, so no backend is needed (great for UI work). Live mode: the frontend talks to the real backend. A single setting switches between them (section 9).

Two important backend files

  • schemas.py: defines the exact shape of every response. Python uses snake_case (online_devices) but the JSON is sent as camelCase (onlineDevices) to match the frontend.
  • tests/: 90 automatic tests (pytest). AWS tests use moto, a fake AWS, so they cost nothing.
  • Devices, agent and alerts endpoints were designed frontend-first and are documented in docs/api/frontend-contract.md → "Devices, agent and alerts (implemented)".

7. Following one request, step by step

Here is exactly what happens when the Devices page shows its table, in live mode. This is the same pattern for every piece of data in the app.

  1. You click Devices in the sidebar. React Router sees the URL /devices and shows pages/DevicesPage.tsx (rule in App.tsx).
  2. The page renders <DeviceTable />. The table calls useApi(getDevices, {'{'} live: true {'}'}), so it shows a grey loading placeholder.
  3. getDevices() in services/dashboardService.ts checks the mode. In live mode it calls apiClient.get("/devices").
  4. apiClient (axios) adds your login token if you have one and sends GET http://localhost:8000/api/devices.
  5. The backend's main.py checks the request comes from an allowed website (CORS) and passes it to routers/resources.py → list_devices().
  6. The router returns the device list. Pydantic (schemas.py) checks the shape and converts it to JSON.
  7. The JSON travels back. useApi stores it, and DeviceTable draws the rows, status badges and coloured usage bars (green / amber over 70% / red over 90%).
  8. Every 30 seconds RefreshProvider repeats steps 3–7 in the background, keeping the old rows on screen until new ones arrive.
  9. If anything fails (backend down, error), the panel shows "Couldn't load devices" with a Retry button.
Rule of thumb for changes New screen? Add a page + route + menu item. New data? Add a type, mock data, a service function, then a backend endpoint, and document it in docs/api/frontend-contract.md.

8. AWS integration

The backend reads real data from AWS using boto3, the official AWS library for Python. It only ever reads; it never creates or changes anything in AWS.

Important things to know

  • Credentials never go in Git. The backend finds them in your computer's AWS profile (aws configure --profile cloudopshub, then set AWS_PROFILE=cloudopshub).
  • Least privilege: the IAM user has only 3 permissions. Even if its keys leaked, it couldn't delete or create anything.
  • Free plan limitation: AWS Free plan accounts block listing EC2 from code (an AWS-managed "service control policy"). The console still works. The AWS Cloud page explains this when it happens.
  • Cost safety: STS and EC2 listing are free; CloudWatch has a large free quota. The frontend never auto-refreshes AWS data, only when you click refresh. The future billing feature (Cost Explorer) costs $0.01 per call, so it must also stay manual and should be cached.
  • Errors are friendly: if AWS refuses, the backend returns a clean 502 with AWS's message, and the page explains likely causes (no credentials, missing permission, Free plan).

Future: monitoring many AWS accounts

The plan (in docs/architecture/aws-integration.md) is the pattern used by commercial tools: each monitored account gets a read-only role, and the backend temporarily "becomes" that role (sts:AssumeRole) to read it. No long-lived keys per account.

9. Mock data vs real data

Mock data lets everyone build and demo the app without a backend, a database or AWS. The switch is one line in frontend/.env.local:

What's real today, and what's still sample data

FeatureStatusNotes
Login, tokens, roles, user managementRealStored in SQLite on the backend
AWS account, EC2 list, EC2 CPURealNeeds AWS credentials; blocked on Free plan accounts
Devices, metrics, summary, chartsRealReported by the agent, stored in the app database (B1–B3)
Alerts and notificationsRealRaised and resolved by the alert engine; critical ones go to Discord / SNS (B4, B9)
Accounts pageSampleThe only page still on sample data
Billing / cost panelReal or sampleCost Explorer when AWS allows it, sample data otherwise (PR #12)
Mock modeOptionalVITE_USE_MOCK=true runs the whole frontend without a backend (UI work, demos)
Why this order makes sense Building the screens and API on sample data first means the hard part (collecting real metrics from homelab devices and clouds) can be added later without changing the frontend: only the backend data source changes.

13. Glossary

TermMeaning in plain words
APIThe set of addresses (endpoints) the frontend can call to ask the backend for data.
EndpointOne API address, e.g. GET /api/devices.
JSONA simple text format for data: {"hostname": "nas-01", "cpu": 12}.
ReactA JavaScript library for building user interfaces out of components.
ComponentA reusable piece of the screen, like a table or a chart.
HookA reusable piece of React logic, like useApi (fetch data + loading state).
TypeScriptJavaScript with types, so mistakes are caught before the app runs.
ViteThe tool that runs the frontend dev server and builds the final website files.
FastAPIA Python framework for building APIs; also generates the /docs page.
PydanticChecks that data has the right shape and converts it to JSON.
CORSA browser safety rule; the backend lists which websites may call it.
JWT / tokenA signed digital pass proving who you are. Access token = short-lived, refresh token = long-lived.
bcrypt / hashA one-way scramble of a password, so the real password is never stored.
RBAC / roleRole-based access control: what you can do depends on your role (admin, operator, viewer).
401 / 403 / 502HTTP errors: 401 = not signed in, 403 = signed in but not allowed, 502 = an upstream service (AWS) failed.
boto3The official Python library for calling AWS.
IAM / least privilegeAWS identity and permissions; give only the permissions that are truly needed.
STS / EC2 / CloudWatchAWS services: identity check / virtual servers / metrics and monitoring.
SCPService control policy: an account-wide AWS rule that can block actions even if IAM allows them.
Mock dataFake sample data used for development and demos.
Docker / containerA packaged app with everything it needs, so it runs the same everywhere.
nginxA web server; here it serves the website and forwards /api calls to the backend.
CI / CDContinuous integration (automatic checks on every change) / continuous deployment (automatic release).
Pull Request (PR)A request to merge your branch into main, where others review it and CI checks it.
TerraformInfrastructure as code: describe cloud resources in files and create them automatically.
AgentThe small program on each monitored device that reports its numbers every minute.
SSMAWS Systems Manager: stores the JWT secret (Parameter Store) and gives admin shell access without SSH (Session Manager).
